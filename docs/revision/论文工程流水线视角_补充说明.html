为什么上一份里看不到“项目开发”

三个原因，前两个是组织方式的问题，第三个是真正的缺口。

  1. 组织维度不同上一份是“诊断式”的：按章节列问题、按问题给改法。你的思路是“生产式”的：按工作先后排步骤。内容其实大部分都在，只是被拆散到了“一致性问题清单”“实验重做方案”“原型系统怎么写”几个地方，没有串成一条线。
  2. 数据处理这一步你已经做完了口径冻结文件（11/13）已经把切分、建图范围、边权重、正负样本全部定死，所以上一份只在 W1 安排了“跑 verify 脚本 + 打 tag + 画数据画像”，看上去像没有这一步。
  3. 工程线确实漏排了上一份只在 W7 安排了原型的“测试和截图”，没有安排“把新训练的模型接进原型”。可原型现在用的大概率是旧口径下的模型：TI-LightGCN 重训后嵌入会变，Temporal-DIN 要换成新的短期通道和蒸馏版本，User Memory 要用本地模型重新生成。这些产物要导出、建索引、替换、再重测延迟和内存，至少两到三周的工作量，必须和实验并行，不能压到最后一周。

另外，你的三步版本少了三个环节（上图红色虚线框），恰好是上一份列为“必须改”的问题的来源：

评估框架夹在数据和基线之间。基线和你的模型必须走同一个评估函数，否则对比不成立。表 5-7 里完整系统和单独 TI-LightGCN 的 Recall@10 一模一样，就是因为端到端指标没有统一的评估入口。

“部署”在你的项目里出现两次，含义不同。第一次是 W5 用 vLLM 本地部署 7B 模型当离线教师，这是实验的一部分；第二次是 W6–7 把模型产物部署进原型服务，这是系统章的内容。混在一起想，就容易把教师打分写成“调用 API”，也容易把系统延迟写成实验指标。

端到端评估是召回和排序训练完之后单独的一步：在精排后的列表上重新算指标，召回没命中就算没命中。

S1 评估框架

你的版本里缺W1

最容易被跳过的一步。没有它，基线、你的模型、端到端三套数字各算各的，表格之间对不上。

做什么
统一评估入口：全排序、屏蔽训练和验证物品、按用户输出明细（每个用户的测试物品排名）。按用户配对检验的脚本也在这一步写好。规定每次运行的结果目录结构，写 make_tables.py 直接从结果目录生成论文表格。
与 RecBole
基线用 RecBole 跑，就把 TI-LightGCN 也作为自定义模型接进 RecBole，共用它的评估器。自写的 eval.py 用来交叉校验一次（同一个 LightGCN checkpoint 两边算出来应一致）和输出按用户明细。
验收
同一 checkpoint 评估两次结果逐位一致；RecBole 与 eval.py 对 LightGCN 的结果一致。
喂给
实验设置小节、评价指标公式、全部结果表、显著性检验。

还可能卡住的地方

都是按流水线思考时容易冒出来的问题。

先做实验还是先做系统？

实验优先，系统并行。论文的结论靠研究线的数字，系统线只产出延迟、内存、截图和测试用例。但系统不能拖到最后：W3 用 v0 打通之后，后面每次只是换版本号，工作量是线性的；拖到最后一次性接，问题会集中爆发。

原型里的模型必须和实验里的完全一样吗？

代码和导出流程必须一样，数据范围可以不同。离线实验只用训练集建图和训练；原型演示可以用截至最后时间点的全部历史重训一次，这是线上系统的正常做法。系统章写一句说明两者的区别，并在 manifest.json 里记下各自的数据范围即可。

开发工作量在论文里体现不出来，会不会显得工作量不够？

工作量通过第 5 章的设计、实现和测试体现，不是通过描述开发过程体现。评审看的是：设计有没有对应的实现，测试数字是不是真测的，系统和算法章节是不是同一套东西。E1 和 E3 里那两条“原型列表与离线评估列表一致”的验收，恰好可以作为系统章的一条测试用例写进去，证明系统确实运行的是论文里的模型。

RecBole 跑基线之后，原型怎么用 RecBole 训出来的模型？

不需要让原型依赖 RecBole。召回模型训练完只导出用户和物品向量，原型用 FAISS 做内积检索；Temporal-DIN 导出 PyTorch 权重和特征词表，原型里只保留前向推理部分。导出脚本负责把 RecBole 内部 ID 映射回原始 user_id/item_id，这一步最容易出错，所以 E1 的验收要专门对比一个用户的列表。

时间不够时工程线先砍什么？

按顺序砍：降级逻辑的完备性 → 混合缓存场景的压测 → 截图数量。不能砍：v0 打通、v2 接入后的列表一致性校验、一次真实压测。系统章至少要有一张真实的性能表和一份功能用例表。
