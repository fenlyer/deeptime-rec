两份分析的共识

两份分析在大方向上一致，以下几点可以直接作为结论：

  • 不用 RecBole 处理好的 Amazon 数据替换你的数据。论文的统计数字、冷启动比例、复杂度和显存估算都绑定在官方 5-core 文件的实测值上。
  • RecBole 的模型不认识 αr 反馈强度和时间衰减边权，没有硬负池采样，也没有长尾语义正则。TI-LightGCN 不能直接用 RecBole 现成模型代替。
  • 排序阶段（Temporal-DIN、LLM 蒸馏）和系统层实验与 RecBole 无关，继续自研。
  • RecBole 最大的价值是基线：用你自己的划分跑官方实现，需要一个 adapter 把 processed/ 数据喂进去。
  • 引入 RecBole 前先在 docs/decisions.md 登记，并保证 eval/、configs/eval.yaml、切分和屏蔽规则不变。这一点是 Claude Code 提出的，符合你项目的红线流程，应当采纳。

需要修正的几处判断

Claude Code 的分析里有几条事实判断不准确。结论方向不受影响，但如果照原样写进 decisions.md 或答辩材料，会被懂 RecBole 的老师指出来。

原判断实际情况影响
RecBole 内置的 Amazon 通常是 2014/2018 版，所以数字对不上。 RUCAIBox 的 RecSysDatasets 已收录 Amazon 2023 的转换脚本和处理好的文件。不用它的真正原因是处理口径（主键、去重、过滤顺序）不一定和官方 benchmark 文件一致，而不是版本旧。 结论不变，理由要换。
RecBole 的 LightGCN 默认在全量交互上构图，可能包含 test，与防泄漏设计冲突。 RecBole 的标准流程用训练集的 dataset 实例化模型，LightGCN 的邻接矩阵取自这个训练集的交互矩阵，测试交互不进图。嵌入表覆盖全部 ID，这和你的实现一样。 不构成阻碍。可以加一条校验：邻接矩阵非零数 = 训练对数。
你的 LOO 以 (user, item) 对为单位，RecBole 按行为记录切，会跨 split 泄漏。 IS/TH/OP 的 5-core 文件实测重复对为 0，一行就是一对，两者完全等价。AJ 的多行为数据由 adapter 先聚合成一行一对再导出即可。另外，用 benchmark_filename 加载预切分文件时，RecBole 根本不做切分。 由 adapter 消除。
.inter 文件没有连续权重的概念。 atomic 文件支持 float 字段，rating、timestamp、权重都能存。不支持的是模型：现成模型不读这些列。 不兼容在模型层，不在格式层。
RecBole evaluator 没有分层分析和配对检验，所以不能用。 确实没有，但这不妨碍用 RecBole 训练：导出嵌入后在 eval/ 里算，分层和检验照常进行。 正是本方案的做法。

唯一的分歧：基线在哪里训练

Claude Code 的主推荐是“参考 RecBole 的 PyTorch 实现，在你自己的训练循环里重写基线”，把 RecBole adapter 当作备选。我的建议正好相反，adapter 方案应当是主方案，理由有三条。

  • 说服力。论文能写“基线均采用 RecBole / RecBole-GNN 官方实现”，基线是否被压低这类质疑基本不会出现。自己重写的基线，审稿人无从核对。
  • 风险。SGL 的图增广、SimGCL 的噪声扰动细节多，自己重写容易出隐蔽 bug，而且这些 bug 都会让基线变弱，最终看起来像是你的方法更强。
  • 红线。RecBole 只负责训练，评估仍走 eval/，不碰评估代码、配置、切分和屏蔽规则，完全满足红线第 3 条。

重写方案唯一的优势是不用多装一个框架。代价是单独建一个 conda 环境（RecBole 与 Python 3.12、NumPy 2.x 的组合可能有依赖问题，建议用 Python 3.10），这个代价不大。

落地步骤

  1. 登记决策 在 docs/decisions.md 写一条记录，草稿见本页末尾。先登记再动代码。
  2. 写 adapter 新增 scripts/export_recbole.py，读 processed/{name}/ 的 train、val、test，写成 dataset/{name}/{name}.train.inter、.valid.inter、.test.inter。表头用 RecBole 的类型标注： 
    user_id:token	item_id:token	rating:float	timestamp:float
    一行一个 (user, item) 对。AJ 先按对聚合，再导出。
  3. 基线配置单独放 新建 configs/recbole_baselines.yaml，与 configs/eval.yaml 分开。关键是关闭 RecBole 自己的过滤，不让它改动你的数据： 
    dataset: IS
benchmark_filename: [train, valid, test]
load_col:
  inter: [user_id, item_id, rating, timestamp]
user_inter_num_interval: ~
item_inter_num_interval: ~
embedding_size: 64
eval_args: {group_by: user, order: TO, mode: full}
valid_metric: Recall@10
  4. 训练基线 BPR、NGCF、LightGCN、SGL 用 RecBole，SimGCL 用 RecBole-GNN。超参数在 valid 上随机搜索，5 个随机种子，与表 5-3 的说法保持一致。
  5. 导出嵌入并映射回原始 ID 图模型取前向传播后的最终用户和物品嵌入，BPR 取嵌入表。RecBole 内部会重新编号，并且第 0 行是填充位：要先丢掉第 0 行，再用 dataset.field2id_token 映射回原始 user_id 和 item_id，保存为 results/baselines/{model}_seed{k}.npz。
  6. 统一进 eval/ 基线嵌入和 TI-LightGCN 嵌入走同一个评估入口：全排序、同一屏蔽规则、冷启动分层、配对 t 检验，结果写入 thesis/generated/numbers.json。
  7. 对账校验 按你的 verify 脚本习惯，新增一个 verify_recbole_adapter.py，检查项见下一节。

对账校验

这一步决定了 RecBole 基线能不能放心写进论文。四项检查都通过，就可以在 5.1.2 加一句“基线训练与本文模型共享同一划分文件与评估器，并经逐项对账”。

检查项通过标准不通过时先查
导出行数与 ID 集合三个 .inter 文件行数分别等于 train/val/test 对数；用户和物品集合与 processed/ 完全相同。RecBole 过滤是否真的关掉。
邻接矩阵只含训练集RecBole LightGCN 交互矩阵的非零数等于训练对数。模型是否用训练集 dataset 实例化。
RecBole 指标与 eval/ 对账同一份嵌入，RecBole 内部的 Recall@10 与 eval/ 的结果一致或差异极小。RecBole 测试阶段屏蔽的是 train 还是 train+valid，与 eval/ 的屏蔽规则逐条比对。
LightGCN 双实现校准你 PyG 版的原始 LightGCN 与 RecBole 版在同一划分上的 Recall@10，差距落在随机种子波动范围内。归一化方式、层组合、L2 正则的写法。

需要提前定下的公平性口径

基线的训练正样本用哪些对。TI-LightGCN 的图用全部训练对加权，BPR 正样本只取 rating≥4。RecBole 基线默认把训练文件里的每一行都当正样本。如果不说明，答辩时可能被问：提升来自边加权，还是来自正样本过滤？

建议：主表基线用全部训练对，这是最常见的标准做法；另加一行“LightGCN（仅 rating≥4 训练对）”作为补充。因为是预切分文件，只需过滤 train 文件，valid 和 test 不动，划分不受影响。再配合表 5-11 的“去掉反馈强度权重”消融，就能把过滤和加权的贡献拆开。

测试目标里的低分交互。训练时把 rating≤2 当硬负样本往下压，测试时又把 rating≤2 的最后一条当召回目标（约 11.2%）。口径本身说得通，因为用户确实发生了购买。但建议在 5.1.1 补一句：测试衡量的是“下一次交互”，不是“下一次满意交互”。
